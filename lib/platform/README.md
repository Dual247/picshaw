# Platform core integration contract

- `core.ts` is provider-independent. `gsc.ts` is server-only and uses only fixed Google Search Console read endpoints. No live provider calls are made by tests.
- Implement `ConnectionResolver.resolve` on the server. Authenticate the actor and check organization membership, connection ownership and the exact connection ID before returning a token. Never serialize `AuthorizedConnection` to the browser. Missing ownership fails closed.
- `listProperties(actorId, organizationId, connectionId)` supports initial property discovery without a selected property. The resolver authorizes the Google connection independently. `readSnapshot` additionally requires an exact property ID and checks it against Google's readable property list. This module does not implement OAuth, token refresh, storage or sessions.
- `completedWindows` uses Pacific calendar dates with a default three-day lag. These are requested windows, not proof of finalized coverage. Requests are bounded to 1-90 calendar days and use `dataState: final`; retain warnings and retrieval times. If a daily coverage check finds missing dates, suppress comparisons or mark coverage bounded rather than interpreting missing data as zero.
- Read separate snapshots with dimensions `[]` for authoritative aggregate metrics, `['date']` for trend/coverage, and `['page']` for actions. Never display summed query/page rows as property totals. API top rows and anonymized query omissions prevent guaranteed exhaustive coverage even when pagination terminates.
- `buildActions` requires adjacent, equal-length page snapshots of the same workspace/property/filters/timezone. It returns at most three deterministic review actions with current/prior evidence and rule version. Bounded or provider-signaled incomplete snapshots return no actions. Empty/sparse rows are not fictional replacements. Absence of a prior row is not zero historical traffic.
- `buildReport` checks the exact selected current snapshot and copies structured source/evidence data. It does not authorize the caller: perform workspace authorization before loading either snapshot. Render every string as escaped text; do not use raw HTML. There is no hosted share/export endpoint or public report link.
- Persist immutable snapshots server-side. Store action completion/change dates separately from computed recommendations; completion is not proof of SEO improvement.
- Errors carry a stable `code`, never provider response bodies or tokens. Rate limiting/retries and background job scheduling belong to the caller; retry only safe reads with bounded backoff.

Validation: `node scripts/check-platform-core.mjs` runs mocked provider tests. Focused typecheck: `node node_modules/typescript/bin/tsc --noEmit --strict --skipLibCheck --target ES2022 --module esnext --moduleResolution bundler lib/platform/core.ts lib/platform/gsc.ts`.


The current adapter imports ordinary final Google Web Search, not the separate Google Generative AI report. See docs/portal-measurement-contract.md for the current API limits and source separation.


## Reviewed Search Console journey

`journey.ts` is a server-only orchestration contract over `core.ts` and the existing `gsc.ts` reader. It is not a route, live connection, persistence implementation or launched customer sync. Run `node scripts/check-platform-journey.mjs` for its mocked adversarial checks.

- Construct `createSearchJourney` with a trusted `JourneyResolver` and a `readSnapshot` implementation, normally the existing GSC adapter once its real authorization/token resolver is implemented. `run` accepts only organization, connection and exact Google property selections. The journey resolver must authenticate the current server session and verify membership, connection ownership and selected property; browser actor IDs are ignored. The GSC adapter must independently retain its ownership and Google property-access checks. Neither resolver is supplied by this contract.
- Organization and connection identifiers are UUIDs. The service mints a UUID run and six distinct UUID snapshot IDs before reading. It requests separate aggregate (`[]`), daily (`['date']`) and page (`['page']`) snapshots for current and prior adjacent equal-length Pacific windows. The default is 28 days with a three-day lag, not a finality guarantee. Server dependencies may change the bounded window/row limits; the browser cannot supply run IDs, snapshot IDs or arbitrary windows. Domain and URL-prefix property IDs remain distinct and unchanged.
- Every returned source must match its trusted run, organization, property, exact window, grain, empty filters, final Web-search data state and Pacific timezone. Runtime validation rejects invalid metrics, duplicate/out-of-window daily keys, unsafe/out-of-property page links, invalid timestamps and oversized row sets. Only allowlisted data is copied; unexpected token fields are discarded. Requests, result provenance, source snapshots and action evidence are deeply frozen. These in-memory copies do not replace immutable database storage or authorize report access.
- Headline metrics come only from the separately requested aggregate snapshot. Daily rows validate date coverage and reconcile property-level clicks, impressions and impression-weighted position. Page rows are never summed into property totals or reconciled against them: property and page aggregation differ. Available page rows remain non-exhaustive even for a comparison-ready bundle.
- `ready` requires all expected daily dates, aggregate rows, matching daily/property totals and no bounded source among all six snapshots. `empty` additionally requires explicit zero property/daily observations and no observed pages in both periods. An API response containing no rows does **not** establish an empty site. In particular, a missing daily row might mean legitimate zero activity or unavailable data; this contract cannot distinguish them and does not fill it with zero, even when the remaining rows happen to match the aggregate totals.
- `incomplete` covers unknown dates, missing aggregates and bounded/provider-incomplete snapshots. `inconsistent` covers disagreeing daily/property totals or literal zero property activity contradicted by observed positive page activity. The latter is a zero-versus-observed-activity contradiction, not a requirement that page sums match property totals; all original evidence is retained. Both retain observed data and explicit per-window coverage reasons but expose no comparison or actions. `unavailable` contains a sanitized error code and no partial snapshots, totals, comparison or actions; reading stops at the first source failure. Authorization failure throws `UNAUTHORIZED` and never becomes a report or sample result.
- Relative change is null when the prior aggregate is zero. Missing prior page evidence remains null and never becomes zero historical traffic. Actions are generated only after the stronger six-snapshot review, retain their exact current/prior snapshot references and remain review suggestions, not explanations, promises or work-completion records. Render text escaped; even validated page URLs still require ordinary safe external-link handling.

The contract is aligned with the planned tenant database's UUID run/snapshot identities and exact Google property identifiers, but deliberately installs no data writes, routes, OAuth flow, background tasks or provider calls by default. Connecting it to authenticated selection, storage and report presentation remains a separate launch gate.


## Atomic persistence boundary

`persistence.ts` now provides reusable, server-only PostgreSQL transaction orchestration. **It has no production database driver, credential configuration, current-session authority binding, route or enabled runtime integration.** The dedicated database's existence alone does not connect this code to it. No hosted write is performed by constructing the service or running its tests.

Construct `createPersistentSearchJourney` with the existing journey dependencies, a `JourneyDatabase` that acquires one pinned SQL session, and a mandatory `SessionAuthority`. `prepare(selection)` collects and reviews all six snapshots outside any transaction. It returns either the unavailable-source result or a frozen server-local capability containing the review and `commit()`. The commit method accepts no browser IDs, snapshot payload or actor. It retains the exact validated bundle in its closure; JSON serialization does not recreate that capability.

The transaction performs these steps:

1. Re-verify the same non-anonymous actor and session before acquiring a database session. Authentication/network work must finish before `BEGIN`; provider collection also happens beforehand.
2. Start an explicit READ COMMITTED transaction with bounded lock, statement and idle-transaction timeouts. Lock the current same-tenant membership FOR SHARE and exact connection FOR UPDATE. Require active owner/admin membership and an active Google connection with the exact read-only Search Console scope. Member/viewer roles cannot import data. No caller-supplied role is consulted.
3. Run the mandatory database-only `SessionAuthority.lockCurrent` check. It must verify the exact authenticated session and actor, check current revocation/expiry, and retain a conflicting row lock against revocation until commit. It returns the authoritative expiry; the earlier verified token expiry remains an upper bound. There is no noop/default implementation. The ordinary `getUser` helper alone is insufficient for this contract because signed-out access tokens may remain valid until expiry. No `auth.sessions` grant or privileged RPC is added here.
4. Insert the immutable run, all six snapshots, exact derived actions and one private report selection in that transaction. Fixed internal table/column names and parameterized JSON values map the TypeScript contract to the existing schema. The report references the current/prior page pair, but all six source artifacts remain in the same run. Incomplete/inconsistent reviewed bundles may be retained for review with no comparisons/actions; unavailable partial collections are never persisted.
5. Compare every retained supplied field and the exact run-scoped sets of snapshots/actions/reports with the prepared cohort. Database-generated creation timestamps are excluded, and PostgreSQL typed conversion normalizes date/timestamp representations. Missing, additional or different artifacts are `IDEMPOTENCY_CONFLICT`, not a partial success. Check the session deadline again immediately before `COMMIT`.

Membership, role, connection and session changes that acquired their conflicting database locks first are observed and can deny the operation. Changes arriving after these locks must wait until the transaction ends; authorization is serialized at that boundary rather than promising that a later revocation can retroactively undo a completed write. This is not an atomic proof of Google's external token/property permissions at commit: those are checked during collection, while current local connection state is checked in the transaction. Real multi-session lock races still need a hosted/native PostgreSQL test before activation.

**Retries and failure handling:** reuse the exact server-local prepared capability. It mints one report ID and retains one run/snapshot cohort; a replay reauthenticates, takes the same authority locks and verifies every existing artifact before returning `already_committed`. It never upserts or overwrites retained evidence. Insert/check failures roll back; a lost `COMMIT` response is `COMMIT_OUTCOME_UNKNOWN`, and an unconfirmed rollback is `ROLLBACK_UNCONFIRMED`. Neither permits automatic new-run fallback. Failed/uncertain connections must be discarded by the injected driver. Pool cleanup errors cannot disguise a confirmed commit as a failed one.

This in-memory capability is not durable job storage. If the process loses it, a future request must not silently re-collect under a fresh run ID as an HTTP retry. Before adding a stateless Vercel write endpoint, design and review the durable server-owned operation/idempotency record and recovery workflow. Report presentation must reconstruct the six-snapshot reviewed result, not use the older page-pair-only `buildReport` as proof of complete coverage. Work-completion events remain separate and are not inserted by this import.

Validation: `node scripts/check-platform-persistence.mjs` executes the actual parameterized transaction SQL in a fresh PGlite database using the currently discovered local migrations. It needs the same pinned, isolated `validation/tenant-database-tooling/` dependency as `check:database`. Twenty-two tests cover coherent commits, exact retries, serialized same-handle retries, rollback at each insert stage, conflicting stored cohorts, revoked/downgraded memberships, disconnected connections, revoked/expired/changed sessions, lost commit confirmation, immutable evidence and incomplete-source retention. Its session table and source provider are explicitly synthetic; the script accepts no hosted database target or credential. It does not prove production driver, Supabase session binding or independent backend concurrency behavior.

Before activation: review a least-privilege production pinned-session adapter; implement a revocation-safe session authority without broadening browser access; add durable operation recovery; test native/hosted concurrency, failure handling and authorized report reads; and finish the separately approved Google consent/encrypted token lifecycle. No feature flag bypasses these requirements.

References reviewed: [Supabase sessions](https://supabase.com/docs/guides/auth/sessions), [connection pooling](https://supabase.com/docs/guides/database/connecting-to-postgres/pooling-and-limits), and the [current Supabase changelog](https://supabase.com/changelog).
